# MLB Win Probability Engine

イニング・アウト・走者・点差（とカウント）から、**ホームの勝利確率・局面の重要度（Leverage Index）・作戦ごとの勝率の増減**を返すエンジンと、その数字を読んで次の 1 球の前に作戦を提案する **Claude ベンチコーチ**。

**[Live Demo](https://mlb-wp-engine.streamlit.app/)**（English / 日本語）

公開して動いているのは Streamlit デモだけです。FastAPI は手元で起動して使います。デモには API キーを置いていないので、デモからは Claude を呼びません。

---

## エンジン

MLB Stats API の play-by-play から作った打席ごとの遷移（2021〜2025 年・915,418 打席）に当てはめた、リーグ平均のマルコフモデルです（`wp_engine.py`、表は `engine_tables.json`）。

1. レギュラーシーズンの打席で、塁・アウトの状態ごとに「次の状態とその打席の得点」の分布を、表（ビジター攻撃）と裏（ホーム攻撃）で別に数える
2. そこから、半イニングの残りで何点入るかの分布を動的計画法で出す
3. 半イニングを再帰でたどって試合の勝率を出す（サヨナラ、延長の二塁走者〈2020 年以降のレギュラーシーズン。ポストシーズンは無し〉）
4. カウントの層：打席の結果の種類はカウントで変わり、種類ごとの遷移は変わらないとして、カウント別の勝率を出す（0-0 ではカウント無しの勝率と一致）

作戦は得点期待値でなく**勝率**で測ります。

| 作戦 | 出す数字 |
|---|---|
| 盗塁（二塁・三塁） | 損益分岐の成功率 |
| 送りバント | その状態で実際に起きたバントの結果の平均をとった勝率と、その増減 |
| 敬遠 | 打者を一塁に置いた後の勝率と、その増減（守備側から見る） |

### 2026 年（学習に使っていない年）での確認

![2026年：新しいエンジンは旧エンジンより当たる。0.3〜0.5帯は高めに出る](docs/images/engine_2026.gif)

| | Brier | log loss |
|---|---|---|
| このエンジン | 0.15845 | 0.47138 |
| 旧エンジン（手で合わせた正規近似） | 0.15970 | 0.47733 |
| ホーム勝率の定数 | 0.24976 | 0.69266 |

2026 年の 184,327 打席それぞれについて、打席前の勝率をその試合の勝敗で採点しました。7 回以降で 2 点差以内に限ると、旧エンジンとの Brier の差は −0.0045（試合単位のブートストラップで 95% 区間 −0.0073〜−0.0017）です。勝率帯ごとの数字は `reports/engine_check_2026.json` にあります。

**分かっている弱点**：勝率 0.3〜0.5 の帯で高めに出ます（2026 年は 3.3 ポイント。エンジンの学習に使った 2022〜2025 年でも、年により 0.8〜4.7 ポイント）。

### チームの強さを足した補正層（事前登録して 2026 年で確認）

![チームの強さを足すと2026年の勝率予測が良くなった](docs/images/team_layer.gif)

エンジンは両チームをリーグ平均として扱います。そこで、エンジンの勝率と両チームの得失点差（前年と、その年のその日より前の試合）から勝率を出し直す補正層（ロジスティック回帰）を作り、2026 年で採点しました（`research/wp_layer/`。事前登録は採点の前に commit。凍結前の版を誤って 2026 年で走らせ、出力を読まずに消した件は事前登録の文書に書いてあります）。

| | Brier | log loss |
|---|---|---|
| エンジン | 0.15845 | 0.47138 |
| エンジンの勝率だけで較正し直したもの（対照） | 0.15831 | 0.47115 |
| **チームの強さを足した補正層** | **0.15680** | **0.46743** |

補正層は対照より Brier が 0.00151 小さく（試合単位のブートストラップで 95% 区間 −0.00253〜−0.00049）、エンジンより 0.00165 小さくなりました（−0.00270〜−0.00060）。事前登録した 2 つの仮説はどちらも支持されました。差の点推定は試合の序盤ほど大きく、序盤 3 分の 1 で −0.0026、終盤 3 分の 1 で −0.0006 です（区間は出していない参考値）。

0.3〜0.5 の帯の高めの偏りは、補正層でも対照（較正し直しただけ）と同じだけしか変わりません（帯での予測の平均の差 補正層−対照 +0.001、95% 区間 −0.0016〜+0.0036）。帯の偏りの原因がチームの強さだという見立ては、この結果では裏づけられていません。較正し直すことで帯の偏りがどれだけ縮むかは、1 シーズンでは区間が広く分かりません。詳細は [`research/wp_layer/RESULTS.md`](research/wp_layer/RESULTS.md) にあります。

事前登録で決めたとおり、補正層はアプリと API に入れました（係数は採点したものそのまま・`team_layer.py`）。レギュラーシーズンの試合では、ライブ表示とリプレイでエンジンの勝率と並べてチーム力込みの勝率を出し、`/wp/live/{gamePk}` は `team_layer` で返します。得失点差は MLB Stats API の日程から学習時と同じ規則（終わった試合だけ・継続試合は最初の日に 1 回・その日より前の試合・n/(n+30) で縮める）で作ります。2025 年の全 2,430 試合で学習時の値と一致し（差 0）、2026 年の採点の予測も再現することを `scripts/check_team_layer.py` で確かめています。カウントは使いません（学習が打席前の状態のため）。ポストシーズンの試合と、手で入力する分析には使いません。

### 選手を入れた層（事前登録して 2026 年で確認）

![選手を入れるとエンジンより当たる。チーム補正層とは区別できない](docs/images/player_layer.gif)

エンジンは全選手をリーグ平均として扱います。選手を入れた層（`research/player_layer/`）は、打者・投手・球場から打席の結果（三振・四球・単打・二塁打・三塁打・本塁打・凡打）の確率を出し（その日より前の成績だけを使う）、実際の打順で次に打つ打者たちと、その回に投げる投手（先発は 6 回まで、その後はブルペン）で、残りの全イニングの得点の分布を出して勝率にします。全員を平均にするとエンジンの値と一致することを確かめています。設計は 2021〜2025 年だけで行い（1 シーズンずつ外して採点）、2026 年は事前登録を凍結してから 1 回だけ採点しました。2026 年はこれまでにエンジンの確認・チーム補正層・盗塁研究で使っています。

| | Brier | log loss | 勝率 0.3〜0.5 の帯の偏り |
|---|---|---|---|
| エンジン | 0.15845 | 0.47138 | +3.26 ポイント |
| チームの強さを足した補正層 | 0.15680 | 0.46743 | +1.09 ポイント |
| **選手を入れた層** | **0.15676** | **0.46700** | +1.67 ポイント |

- 勝率：選手を入れた層はエンジンより Brier が 0.00169 小さく（試合単位のブートストラップで 95% 区間 −0.00310〜−0.00024）、事前登録した仮説は支持されました。
- その回にあと 1 点以上入るか：log loss がエンジンより 0.00146 小さく（−0.00198〜−0.00096）、支持されました。
- チーム補正層との差は −0.00003（−0.00098〜+0.00097）で、2026 年では区別できません（同じだという意味ではありません）。

詳細は [`research/player_layer/RESULTS_2026.md`](research/player_layer/RESULTS_2026.md) にあります。事前登録どおり、この層はベンチ画面の数字（代打・継投・バント・敬遠の比較）の土台にし、見出しの勝率は 2027 年の確認まで今のエンジンと補正層のままにします。

### 選手層とチーム補正を混ぜたもの（事前登録して 2026 年で確認）

![BLEND は数字の上では最小だが区間が0をまたぐ](docs/images/blend.gif)

選手を入れた層とチーム補正層を、それぞれ 2022〜2025 年の「学習に使っていない年の予測」で較正し直してから半々に混ぜたもの（BLEND）を、2026 年で 1 回だけ採点しました（`research/player_layer/RESULTS_BLEND_2026.md`）。2026 年で選手層とチーム補正がほぼ同じだと分かった後に設計したので、初見の検証ではありません。

| | Brier | 勝率 0.3〜0.5 の帯の偏り |
|---|---|---|
| チーム補正層 | 0.15680 | +1.09 ポイント |
| 選手を入れた層 | 0.15676 | +1.67 ポイント |

### 終盤の継投の使い方を入れて較正し直した層（事前登録して 2026 年で確認）

![終盤の継投の使い方を入れて較正し直すと、2026年の勝率予測がはっきり良くなった](docs/images/pen_recal.gif)

選手を入れた層の 7 回以降を「そのチームが直近 30 日、その回・その点差で誰を使ってきたか」で割り振り（上の「終盤の継投」と同じ作り方）、2022〜2025 年の「学習に使っていない年の予測」で較正し直したもの（PEN_RECAL）を、事前登録して 2026 年で 1 回だけ採点しました（`research/player_layer/PREREG_PEN.md`、[`RESULTS_PEN_2026.md`](research/player_layer/RESULTS_PEN_2026.md)）。設計は 2022〜2025 年だけで行い、どの年もエンジン＋チーム補正の形より Brier が 0.0015〜0.0021 小さくなっていました。

| | Brier | log loss | 勝率 0.3〜0.5 の帯の偏り |
|---|---|---|---|
| エンジン | 0.15845 | 0.47138 | +3.26 ポイント |
| チーム補正層（これまでの見出し） | 0.15680 | 0.46743 | +1.09 ポイント |

- チーム補正層より Brier が 0.00173（試合単位のブートストラップで 95% 区間 −0.00262〜−0.00076）小さく、支持されました。
- 選手を入れた層（v1）より 0.00170（−0.00227〜−0.00112）小さく、支持されました。
- 2026 年はこれまでの検証で何度も使っていて、v1 とチーム補正がほぼ同じことや、較正の効き方も分かったうえで設計しています（事前登録の文書に書いてあります）。初見のデータでの確認は 2027 年です。

事前登録で決めたとおり、振り返り（2022〜2026 年の終わった試合）で見せる勝率をこの層に切り替えました（下の「振り返り」）。ライブと API は、2027 年に確かめるまでチーム補正層のままです。

### 救援投手の起用を直近 60 日で数える（事前登録して 2026 年で確認）

![救援投手の起用を直近60日で数えると、2026年の勝率予測がわずかに良くなった](docs/images/penw.gif)

上の層の「誰が何回・どの点差で投げるか」を、直近 30 日ではなく直近 60 日の起用から数えたもの（PENW_RECAL）です。2022〜2025 年だけで比べたところ（2026 年は見ていません）、60 日はどの年も 30 日より Brier が小さく（−0.000093、95% 区間 −0.000118〜−0.000068）、120 日も同じく良かったものの 60 日に届きませんでした。また、救援投手の役割をチーム内でシャッフルする診断では、継投の層の上積みのおよそ半分が「役割（どの回・どの点差で誰を使うか）」から来ていました（`research/player_layer/README.md`）。

これを事前登録して 2026 年で 1 回だけ採点しました（`research/player_layer/PREREG_PENW.md`、[`RESULTS_PENW_2026.md`](research/player_layer/RESULTS_PENW_2026.md)）。

| | Brier | log loss | 勝率 0.3〜0.5 の帯の偏り |
|---|---|---|---|
| チーム補正層 | 0.156797 | 0.46743 | +1.09 ポイント |
| 直近 30 日（PEN_RECAL） | 0.155063 | 0.46314 | +0.64 ポイント |
| **直近 60 日（PENW_RECAL）** | **0.154977** | **0.46295** | +0.60 ポイント |

- 30 日より Brier が 0.000086 小さく（95% 区間 -0.000133〜-0.000037）、支持されました。差は小さく、30 日の層がチーム補正層より良くなった分の 5% ほどです。
- 2026 年は 30 日の層の採点にも使っていて、その結果を知ったうえでの検証です（事前登録の文書に書いてあります）。

事前登録で決めたとおり、振り返りで見せる勝率と、ベンチの選択肢の中の終盤の継投は 60 日に切り替えました。「起用パターン」（監督の選択との一致を調べたときの決まり）は 30 日のままです。

### 救援の役割を細かく見る（事前登録して 2026 年で確認）

![救援の役割を細かく見ると、2026年の勝率予測がさらに良くなった](docs/images/penr.gif)

上の 60 日の層をもとに、救援の役割の見方を 2 点変えたもの（PENR_RECAL）です。
- 点差の分け方を 4 段階から 5 段階に（ビハインドを「3 点以上」と「1〜2 点」に分ける）。
- そのチームの使い方をほぼそのまま使う（これまでは使った打席数が少ないほどブルペン全体の平均に寄せていた。その寄せ方をほぼなくした）。

2022〜2025 年だけで比べたところ、どの年も 60 日の層より Brier が小さくなりました（−0.000179、95% 区間 −0.000214〜−0.000146）。ただし、試した中でいちばん良かった設定を選んでいるので、この数字は甘めです。点差を 6 段階にする（リードも 1 点と 2〜3 点に分ける）と、逆にどの年も悪くなりました。

事前登録して 2026 年で 1 回だけ採点しました（`research/player_layer/PREREG_PENR.md`、[`RESULTS_PENR_2026.md`](research/player_layer/RESULTS_PENR_2026.md)）。

| | Brier | log loss | 勝率 0.3〜0.5 の帯の偏り |
|---|---|---|---|
| チーム補正層 | 0.156797 | 0.46743 | +1.09 ポイント |
| 直近 60 日（PENW_RECAL） | 0.154977 | 0.46295 | +0.60 ポイント |
| **役割を細かく見た層（PENR_RECAL）** | **0.154793** | **0.46256** | +0.66 ポイント |

- 60 日の層より Brier が 0.000184 小さく（95% 区間 -0.000269〜-0.000107）、支持されました。60 日の層がチーム補正層より良くなった分の 10% ほどです。
- 支持されたのは 2 点を合わせた設定です。2022〜2025 年では、上積みの大半は「平均に寄せない」ほうから来ていました。
- 勝率 0.3〜0.5 の帯の偏りは 60 日の層より少し大きくなりました（検定はしていません）。

事前登録で決めたとおり、振り返りで見せる勝率をこの層に切り替えました。ベンチの選択肢の中の継投と「起用パターン」は変えていません。

### ベンチの選択肢（ライブ表示）

試合中のライブ表示に「ベンチの選択肢」を出します（`bench_live.py`）。MLB Stats API のライブフィードから、今の打順・控えの野手・まだ投げていないブルペン（2025〜2026 年に主に先発した投手は除く）・両チームの次の打者を読み、選手を入れた層で選択肢ごとに「この回の得点期待値」「1 点以上入る確率」「攻撃側の勝率」を出します。

- 攻撃側：そのまま／送りバント／盗塁（その走者の成功見込みと損益分岐の成功率を並べて「走れ／走るな」）／代打（控えの全員を計算し、勝率の高い順に最大 6 人）／代走（今の走者より速い控え、最大 3 人）
- 守備側：敬遠／継投（ブルペンの全員を計算し、相手の勝率を下げる順に最大 6 人）

選手の成績は 2021〜2026 年のレギュラーシーズン（`research/player_layer/published/bench_snapshot.json`、2026-09-27 まで）で、古い年ほど軽く数え（1 年ごとに 0.6 倍。打席の結果の予測で log loss −0.00088）、左右の相性も入れています（−0.00064）。シーズン中は更新されません。サイドバーの「📋 Bench」を選ぶと、試合中の試合を自動で選び、30 秒ごとに更新する 1 画面になります（`bench_screen.py`、図は `bench_viz.py`）：塁とアウトの図、勝率と重要度（勝負所では光る）、今の打者と次の 3 人の結果の内訳（積み上げ棒）、試合の勝率の流れ（大きく動いた 3 プレーに印、「▶ 試合を再生」で線が伸びていく）、盗塁の「走れ／走るな」の札、作戦ごとの勝率の増減（棒）。表でも見られます。

![ベンチ画面（2026-09-20 PHI@NYM の 7 回裏を記録から再現。tools/fake_bench_app.py）](docs/images/bench_screen.png)

### 終盤の継投（投手ごと）

7 回以降の救援を、ブルペン全体の平均ではなく「そのチームが直近 60 日、その回・その点差（3 点以上ビハインド／1〜2 点ビハインド／同点／1〜3 点リード／4 点以上リード）で誰を使ってきたか」の割合で割り振ります（振り返りの勝率と同じ決まり。2026-10-28 までは 30 日・4 段階で、ブルペン全体の平均にもっと寄せていました）。その試合で既に投げた投手と、2 日連続で登板した投手は外します。継投の選択肢では、交代した投手は後の回に使えなくなるので、「今クローザーを使うと 9 回がいなくなる」損も入ります。画面には「終盤の継投の見込み」（今の点差で 7・8・9 回を誰が投げそうか）を出します。

2022〜2025 年で 1 シーズンずつ外して比べると（2026 年は見ていません、733,260 打席）、ブルペン平均の版より Brier −0.00163（95% 区間 −0.00187〜−0.00141）、どのシーズンも改善しました（`research/player_layer/README.md`）。勝ち負けの見分けは良くなった一方、中間の確率がやや控えめに出る傾向が強まっています（0.3〜0.5 帯の偏り +1.9 → +2.7 ポイント）。使い方の記録は 2022〜2026 年の試合だけにあり、それ以外（今後のライブなど）はブルペン平均のままです。

![終盤の継投の見込み（2025-09-06 LAD@BAL 7 回表、守備側オリオールズ 0-3）](docs/images/pen_plan.png)

### 振り返り（終わった試合を 1 打席ずつ）

ベンチ画面の「振り返り」で、日付から（その日の試合）またはチームから（チームと年を選ぶと、その年の終わった試合が新しい順に「09/27 @ SD 4-9 負」の形で並ぶ）試合を選ぶと、各打席の直前の局面を当時のまま再現して、ライブと同じ図を出します（`bench_review.py`、再現は `bench_replay.py`）。

- その時点の打順・まだ使っていない控えとブルペン・走者を、試合の記録（途中交代の記録を含む）から組み立てます。代打が送られた打席では、代打を送る前の打者で計算するので、代打が「選択肢の 1 つ」として評価されます。
- 選手の成績はその試合の前年までのもの（`bench_snapshot_<年>.json`）で、後から分かった成績は使いません。
- 「実際には」の欄に、監督がしたこと（代打・代走・継投・盗塁・バント・敬遠）と、それをモデルがどう評価したか（候補の中の順位と勝率の増減）、打席の結果と勝率の動きを出します。
- 6 回以降の継投では、「普段の起用パターンなら誰か」（そのチームが直近 30 日、その回・その点差でいちばん多く使った、使える投手）も並べます。監督の選択と同じなら「普段の起用パターンどおり」と出ます。2026 年の継投テストでは、この選び方のほうがモデルの最善候補より監督と一致しました（28.7% と 20.1%、上の「継投・代打」の節）。試合のまとめの表にも「起用パターン」の列があります。

![継投の場面：モデルの評価と普段の起用パターン（2025-09-06 LAD@BAL 9 回裏）](docs/images/review_usage.png)
- 同じ打席の中で先に交代があった采配（例：継投の直後の代打）は、その交代のあとの状況で評価します（局面のカードと試合のまとめで同じ評価になります）。
- 局面は、スライダー、前／次、「采配の場面」の一覧、「勝負所へ」（重要度がいちばん高い打席）、「山場」のボタン（勝率がいちばん大きく動いた 5 打席を試合の順に。例「9裏 +74」＝攻撃側の勝率が 74 ポイント上がった打席）、勝率のグラフの点のタップで移れます。
- 2022〜2026 年のレギュラーシーズンの試合では、勝率（大きな数字とグラフ）を「選手・終盤の継投の使い方込み」の層（上の事前登録した検証で、チーム補正層より当たった層。2026-10-28 からは継投の起用を直近 60 日で数え、役割を細かく見た版。打席ごとの値は `research/player_layer/published/pen_wp_<年>.parquet`、`pen_wp.py`）で出します。それ以外の試合とライブはチーム補正層のままです。

![振り返り（2026-09-20 PHI@NYM、7 回裏 1 死一二塁で代打ベイティ。モデルの評価 +0.7 ポイント、候補 7 人中 2 位。実際は適時打で勝率 16%→28%）](docs/images/review_screen.png)

#### 試合のまとめ（1 試合の采配を一覧で）

振り返り画面の「📝 試合のまとめ」で、その試合の代打・代走・継投・盗塁・バント・敬遠をすべて並べ、打席の前にモデルがどう見ていたかを出します。

- **モデル評価**：その采配で、采配したチームの勝率が「何もしない」よりどれだけ上がると見ていたか（ポイント）。代打・代走・継投は、同じ種類の候補の中での順位と、最善の候補との差も出します。盗塁は「走れ／走るな」の判定（成功見込み／必要な成功率）。
- **結果と勝率の変化**：実際に起きたこと（運を含む）。モデル評価とは別物で、結果が良くても悪くても采配の良し悪しの証明にはなりません。
- 図：点＝実際の采配、白丸＝同じ種類で最善の候補（線の長さ＝最善との差）。表の行を選ぶとその局面に移ります。
- 「🔎 モデルならここで動いた」：モデルが 1 ポイント以上の上積みを見ていたのに、その種類の采配がなかった場面を大きい順に 5 つ（全打席を計算するので約 20 秒）。継投は 7 回以降だけ（それより前は、交代後をブルペン平均で計算するため大きく出すぎる）。
- 前年の記録がない選手や、モデルが扱わない場面（満塁の代走など）は「対象外」。守備位置・休養・故障はモデルに入っていません。

![試合のまとめ（2025-09-06 LAD@BAL）](docs/images/summary_screen.png)

代走は、走者の前年のスプリントスピードで余分な進塁（単打で二塁から生還・一塁から三塁、二塁打で一塁から生還）の確率を変えて計算します（2021〜2025 年で 1 シーズンずつ外して採点し、どれも速さを入れたほうが当たる：log loss −0.009〜−0.023）。盗塁の成功見込みは速さだけのモデルで、効きは小さい（−0.0006）ので目安です。守備固めとこの回より先の継投は考えていません。全員を平均の選手にするとエンジンのバント・敬遠の値と一致することを、570 の場面で確かめています（`research/player_layer/selftest_bench.py`）。

## データ

`scripts/build_states.py` が MLB Stats API から打席・走者・投球の表を作ります（GitHub Actions の `build-states.yml` を手動で実行し、Release `states-v1` に出力）。各試合で次を確かめ、どれかが合わない試合は捨てます。

- スコアを打席ごとに積み上げると最終スコアに一致する
- 各半イニングが 0 アウトで始まり、途中でアウト数が減らない
- 延長の二塁走者がルールどおり置かれている
- 盗塁と盗塁死の数がボックススコアと一致する

捨てた試合が 1% を超えたシーズンや、盗塁を投球に割り当てられた割合・捕手の記録が合わないシーズンは書き出しません。2021〜2026 年のレギュラーシーズンの全試合で、捨てた試合は 0 です。表を当てはめ直すときは `scripts/fit_engine.py` を使います。

## Claude ベンチコーチ

`strategist.py` が、局面とエンジンの数字（作戦ごとの損益分岐や勝率の増減）を Claude（`claude-opus-5-5`。混雑時はサーバー側のフォールバックで別のモデルが答えることがあります）に渡し、推奨する作戦・理由・使った数字を構造化出力で受け取ります。**Claude が「使った数字」として返した値と、理由の中の % の数字を、渡した数字と突き合わせ**、合わないものは画面と API の応答に出します。

- キー：環境変数 `ANTHROPIC_API_KEY`（または Streamlit secrets）。無ければ何も送りません
- 1 回の問い合わせは 1 リクエストです（SDK の再試行なし・60 秒で打ち切り。2026-10-15 の実測は 1 回 4〜7 秒）
- アプリでの上限は、サーバー全体で 1 日（UTC）`COACH_DAILY_LIMIT` 回（既定 30）と、1 セッション 10 回です（失敗した問い合わせも数えます）
- API の `/wp/advice` は `ADVICE_TOKEN` も必要です。リクエストに同じ値の `X-Advice-Token` ヘッダーが無ければ断ります（回数の上限は無いので、トークンは人に渡さないでください）

### 盗塁の成功を、統計モデルより当てられるか

![盗塁の成功を Claude は統計モデルより当てられなかった](docs/images/steal_claude.gif)

Claude 自身の予測が役に立つかを、事前登録して確かめました（`research/steal_claude/`）。2026 年 7〜9 月の盗塁 1,843 件で比べた結果、**Claude 単独（log loss 0.4668）は統計モデル（0.4636）より悪く、モデルの予測値を渡した場合（0.4624）は数字の上ではわずかに良いものの、差 −0.0012（95% 区間 −0.0038〜+0.0013）で改善とは言えません**。事前登録した 2 つの仮説はどちらも支持されませんでした。詳細と Claude の全回答は [`research/steal_claude/RESULTS.md`](research/steal_claude/RESULTS.md) にあります。ベンチコーチは、エンジンの数字を言葉にして作戦をまとめる役として使っています。

### 継投・代打で「誰を出すか」は、監督の選択と一致するか

![継投で監督と同じ投手を選んだ割合（2026年7〜9月の422件）](docs/images/bench_claude.gif)

<sub>図は `research/bench_claude/make_gif.py` が `published/results.json` から生成しています（数字は手で写していません。ほかの節の図は `docs/make_gifs.py`）。</sub>

監督が「ここで投手を代える（6 回以降）／代打を出す」と決めた場面で、Claude が監督と同じ選手を選ぶ割合を、事前登録して比べました（`research/bench_claude/`）。2026 年 7〜9 月の 80 試合（無作為抽出）の継投 422 件・代打 165 件が対象です。測っているのは**監督との一致率で、采配が正しかったかではありません**（選ばなかった選手の結果は観測できないため）。

| 継投（422 件、候補は平均 7.3 人、偶然の一致 14.9%） | 一致率 |
|---|---|
| Claude（モデルの数字なし） | 32.7% |
| Claude（モデルの数字あり） | 30.6% |
| 直近の起用パターン（その回・点差で最も多く使われた投手） | 28.7% |
| このアプリのモデル（勝率が最も上がる投手） | 20.1% |

- 仮説 1「Claude（数字あり）＞モデル」：差 +10.4 ポイント（95% 区間 +6.9〜+14.1）で**支持**
- 仮説 2「Claude（数字あり）＞起用パターン」：差 +1.9 ポイント（95% 区間 −3.6〜+7.6）で**支持されず**
- 数字を渡しても一致率は上がりませんでした（数字あり − なし −2.1 ポイント、95% 区間 −6.3〜+2.0）
- 代打は、Claude（数字あり）40.0%、モデル 38.2% で、差は区間に 0 を含みます

読み方：モデルが推す「勝率が最も上がる投手」は、実際の監督の起用とは一致しにくい選び方です。Claude の選び方は、チームの普段の起用パターンに近いものでした。モデルが正しいか監督が正しいかは、この比較からは分かりません。

Batch API が 12 時間進まなかったため、どの答えも読む前に事前登録に変更を書き、通常の呼び出しに切り替えました（Amendment 1）。費用は約 $15、これに試行分とキャンセルした Batch の分（約 $4）が加わります。詳細と Claude の全回答は [`research/bench_claude/RESULTS.md`](research/bench_claude/RESULTS.md) にあります。

## 使い方

### Streamlit

```bash
pip install -r requirements.txt
streamlit run streamlit_app.py
```

- 局面を入力するか、プリセット（9 回裏の満塁など 6 つ）を選ぶと、勝率・LI・作戦・次の打席の結果ごとの勝率が出ます
- **Live Games**：その日の試合を MLB Stats API から読み、進行中の局面をそのまま入力に反映できます（30 秒ごとの自動更新あり。終わった試合は反映しません）
- **Replay Mode**：過去の試合を 1 プレーずつ（自動再生もできます）たどり、各プレーの前後の勝率と WPA を見られます

### FastAPI

```bash
pip install -r requirements.txt
uvicorn api:app --reload
# → http://localhost:8000/docs
```

Docker なら `docker compose up --build` で `http://localhost:8001/docs` です（ホストの `ANTHROPIC_API_KEY` と `ADVICE_TOKEN` を渡します）。

| エンドポイント | 内容 |
|---|---|
| `GET /wp` | 勝率・打撃側の勝率・LI・残りの得点期待値・次の打席の結果ごとの勝率・作戦 |
| `GET /wp/play` | 1 プレーの前後の状態から WPA（`after_outs=3` は攻守交代） |
| `GET /wp/advice` | 上と同じ分析に Claude の推奨を付けたもの（キーとトークンが必要） |
| `GET /re24` | 24 の塁・アウト状態の得点期待値と、1 点以上入る確率 |
| `GET /wp/scenario` | プリセットの局面 |
| `GET /games/today` | その日の試合一覧（`date=YYYY-MM-DD`） |
| `GET /wp/live/{gamePk}` | 試合の現在の局面と勝率（レギュラーシーズンはチーム力込みの勝率 `team_layer` も） |

`/wp`・`/wp/play`・`/wp/advice` は `extra_runner=false` で延長の二塁走者なし（ポストシーズンと 2019 年以前）として計算します。7 イニングの試合は `scheduled_innings=7` を渡します。カウントは `balls` と `strikes` を両方渡したときだけ使います。

```bash
# 9 回裏 2 死満塁 同点
curl "http://localhost:8000/wp?inning=9&top_bottom=bottom&outs=2&runner1=1&runner2=1&runner3=1&score_diff=0"

# Claude の推奨（8 回裏 無死一塁 1 点ビハインド）
curl -H "X-Advice-Token: $ADVICE_TOKEN" \
  "http://localhost:8000/wp/advice?inning=8&top_bottom=bottom&outs=0&runner1=1&score_diff=-1&lang=JA"
```

## 旧版からの変更（2026-10）

- 以前の学習データ（Hugging Face `mlb_wp/play_states`）は、アウト数が全行 0、走者なしが 77% で使えないと分かったため、データを作り直し、エンジンも置き換えました。旧エンジン（v1/v2・LightGBM・ベイズ）と、それに基づく検証値は削除しました（比較用に `scripts/old_engine.py` だけ残しています。アプリと API は使いません）
- 解説は Gemini から Claude に替えました。`/wp/commentary` と `/commentary/info` は無くなり、`/wp/advice` に替わっています
- `runs_per_game`・`batter_ops`・`pitcher_era` による補正は無くなりました（エンジンは全員をリーグ平均として扱います）
